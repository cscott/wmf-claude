# Handoff: AbuseFilter's schema tests fail when the extension is a symlink

Found by the B4 blind run in a wmf-sbx sandbox (2026-10-14,
`sbx/NOTES.md`). Fix it in a sandbox of its own, then give the Gerrit
change and the Phabricator task to the wmf-sbx track, which records them
in `sbx/NOTES.md` and `sbx/upstream/README.md`.

The test that fails is AbuseFilter's, but the cause is in
**mediawiki/core**: `SchemaGenerator::normalizePath()`. The fix probably
goes to core. Any extension whose tests extend `AbstractSchemaTestBase`
fails the same way when it is installed as a symlink.

## What fails

`composer phpunit:entrypoint -- extensions/AbuseFilter/tests/phpunit`
(from core), and core's `--testsuite=extensions`: 11 failures, all in
`AbuseFilterSchemaTest::testSchemasHaveAutoGeneratedFiles` and
`::testSchemaChangesHaveAutoGeneratedFiles`:

```
1) MediaWiki\Extension\AbuseFilter\Tests\Integration\AbuseFilterSchemaTest::testSchemasHaveAutoGeneratedFiles with data set "tables.json" (...)
SQL in /home/cananian/Projects/Wikimedia/Extensions/AbuseFilter/db_patches/mysql/tables-generated.sql for mysql does not appear to be autogenerated. Re-generate it using generateSchemaSql.php.
--- Expected
+++ Actual
 '-- This file is automatically generated using maintenance/generateSchemaSql.php.
--- Source: /home/cananian/Projects/Wikimedia/Extensions/AbuseFilter/db_patches/tables.json
+-- Source: db_patches/tables.json
 -- Do not modify this file directly.
```

Versions: core `977a18621a7`, AbuseFilter `68aa73a3e`.

## Layout that triggers it

wmf-sbx clones each extension at its own place and symlinks it into
core:

```
/home/cananian/Projects/Wikimedia/core/extensions/AbuseFilter
    -> /home/cananian/Projects/Wikimedia/Extensions/AbuseFilter
```

`$wgExtensionDirectory` is core's `extensions/` (the default). WMF CI
(Quibble) clones extensions directly into `core/extensions/`, so CI does
not see this. Developers who symlink extensions into a checkout do (a
common MediaWiki-Docker and mwcli setup).

## Cause

`AbuseFilterSchemaTest` gives `AbstractSchemaTestBase` paths built from
`__DIR__`. PHP resolves symlinks in `__DIR__`, so the JSON path is
`/home/.../Extensions/AbuseFilter/db_patches/tables.json`.

`SchemaGenerator::makeSQLComment()` (core
`maintenance/includes/SchemaGenerator.php`) calls
`normalizePath( $jsonPath, MW_INSTALL_PATH, $wgExtensionDirectory )`,
which calls `realpath()` on all three paths and then:

- if the JSON path starts with `$extensionDirectory/`, it removes that
  prefix and the extension name (`db_patches/tables.json`);
- otherwise it removes `MW_INSTALL_PATH/`.

`realpath( core/extensions )` is core's own `extensions/` directory. The
JSON path is outside both that directory and core, so neither prefix
matches, and the absolute path goes into the `-- Source:` line. The
committed files say `-- Source: db_patches/tables.json`.

The same bug gives a second effect, and it is worse than the failing
test: in such a layout, `generateSchemaSql.php` and
`generateSchemaChangeSql.php` write the absolute path into the generated
SQL files. A developer (or an agent) who regenerates the schema then
commits a header that contains their home directory.

## Proposed fix (core)

In `SchemaGenerator::normalizePath()`, when the resolved JSON path is
under neither directory, find the extension's root another way. Two
options:

1. Walk up from the JSON file to the nearest directory that holds an
   `extension.json` or a `skin.json`, and make the path relative to that
   directory. This does not depend on how the extension was installed,
   and it also handles skins (`$wgStyleDirectory`), which the function
   ignores today.
2. Compare the resolved JSON path against `realpath()` of each entry of
   `$extensionDirectory` (and of `$wgStyleDirectory`). This keeps the
   current logic, but it reads the directory on each call.

Option 1 is simpler, and it is correct for core too: core has no
`extension.json`, so the existing `MW_INSTALL_PATH` branch stays the
fallback. Add a case for a symlinked extension directory to core's
`tests/phpunit/maintenance/includes/SchemaGeneratorTest.php`.

The AbuseFilter side needs no change, unless a reviewer prefers that the
test passes the unresolved path. It cannot: `__DIR__` is resolved
already.

## How to test

In a wmf-sbx sandbox with AbuseFilter (any `create` that names it, or
that has it as a dependency, as Translate does):

```bash
cd "$MW_INSTALL_PATH"
composer phpunit:entrypoint -- extensions/AbuseFilter/tests/phpunit/integration/AbuseFilterSchemaTest.php
# before the fix: 11 failures; after: OK
php maintenance/run.php generateSchemaSql \
  --json extensions/AbuseFilter/db_patches/tables.json --type mysql \
  --sql /tmp/claude-$(id -u)/t.sql && head -3 /tmp/claude-$(id -u)/t.sql
# before: "-- Source: /home/..."; after: "-- Source: db_patches/tables.json"
```

Also run core's own `AbstractSchemaTest` and the structure suite
(`--testsuite=structure`), which run the same code on core's paths.
