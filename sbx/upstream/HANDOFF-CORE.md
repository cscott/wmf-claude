# Handoff: four test failures to fix in mediawiki/core

The B4 blind run in a wmf-sbx sandbox found these on 2026-10-14 (see
`sbx/NOTES.md`). Each fix goes in mediawiki/core. A fix may touch the
tests of an extension, but the code to change is core's.

**These are four separate issues.** Fix each one on its own branch, as
its own Gerrit change, with its own Phabricator task (or a subtask of
the task named below). Do not put two of them in one change. They have
different reviewers, and each one must be able to merge or be reverted
alone. Do them in any order.

|---|---|---|---|---|
| 1 | `schema-generator-symlink` | AbuseFilter PHPUnit; core `--testsuite=extensions` | 11 | `SchemaGenerator::normalizePath()` leaves the path absolute for a symlinked extension |
| 2 | `api-testing-redlink-url` | core `npm run api-testing` | 1 | `ReparseDependentPages.js` expects the `?title=` red-link URL |

## 1. Schema tests fail when the extension is a symlink

### What fails

`composer phpunit:entrypoint -- extensions/AbuseFilter/tests/phpunit`
(run from core), and core's `--testsuite=extensions`, give 11 failures.
All are in `AbuseFilterSchemaTest::testSchemasHaveAutoGeneratedFiles`
and `::testSchemaChangesHaveAutoGeneratedFiles`:

```
1) MediaWiki\Extension\AbuseFilter\Tests\Integration\AbuseFilterSchemaTest::testSchemasHaveAutoGeneratedFiles with data set "tables.json" (...)
SQL in /home/cananian/Projects/Wikimedia/Extensions/AbuseFilter/db_patches/mysql/tables-generated.sql for mysql does not appear to be autogenerated. Re-generate it using generateSchemaSql.php.
--- Expected
+++ Actual
 '-- This file is automatically generated using maintenance/generateSchemaSql.php.
--- Source: /home/cananian/Projects/Wikimedia/Extensions/AbuseFilter/db_patches/tables.json
+-- Source: db_patches/tables.json
 -- Do not modify this file directly.
```

The test that fails is AbuseFilter's, but the cause is in core. An
extension whose tests extend `AbstractSchemaTestBase` fails the same
way if it is installed as a symlink. WMF CI (Quibble) clones extensions
directly into `core/extensions/`, so CI does not see the failure.
Developers who symlink extensions into a checkout do see it.

### Cause

`AbuseFilterSchemaTest` gives `AbstractSchemaTestBase` paths that it
builds from `__DIR__`. PHP resolves symlinks in `__DIR__`, so the JSON
path is `/home/.../Extensions/AbuseFilter/db_patches/tables.json`.

`SchemaGenerator::makeSQLComment()`
(`maintenance/includes/SchemaGenerator.php`) calls
`normalizePath( $jsonPath, MW_INSTALL_PATH, $wgExtensionDirectory )`.
That function calls `realpath()` on all three paths, and then does one
of these:

- if the JSON path starts with `$extensionDirectory/`, it removes that
  prefix and the extension name (`db_patches/tables.json`);
- if not, it removes `MW_INSTALL_PATH/`.

`realpath( core/extensions )` is core's own `extensions/` directory.
The JSON path is in neither that directory nor core, so no prefix is
removed. The absolute path goes into the `-- Source:` line, but the
committed files say `-- Source: db_patches/tables.json`.

The same bug has a second effect, which is worse than the failing test.
In such a layout, `generateSchemaSql.php` and
`generateSchemaChangeSql.php` write the absolute path into the
generated SQL files. A developer (or an agent) who regenerates the
schema then commits a header that contains their home directory.

### Proposed fix

In `SchemaGenerator::normalizePath()`, when the resolved JSON path is in
neither directory, find the extension's root another way. There are two
options:

1. Go up from the JSON file to the nearest directory that holds an
   `extension.json` or a `skin.json`. Make the path relative to that
   directory. This does not depend on how the extension was installed.
   It also handles skins (`$wgStyleDirectory`), which the function
   ignores today.
2. Compare the resolved JSON path with `realpath()` of each entry of
   `$extensionDirectory` (and of `$wgStyleDirectory`). This keeps the
   current logic, but it reads the directory on each call.

Option 1 is simpler, and it is also correct for core. Core has no
`extension.json`, so the existing `MW_INSTALL_PATH` branch stays the
fallback. Add a case for a symlinked extension directory to
`tests/phpunit/maintenance/includes/SchemaGeneratorTest.php`.
AbuseFilter needs no change: its test cannot give the unresolved path,
because `__DIR__` is already resolved.

### How to test

```bash
cd "$MW_INSTALL_PATH"
composer phpunit:entrypoint -- extensions/AbuseFilter/tests/phpunit/integration/AbuseFilterSchemaTest.php
# before the fix: 11 failures; after: OK
php maintenance/run.php generateSchemaSql \
  --json extensions/AbuseFilter/db_patches/tables.json --type mysql \
  --sql /tmp/claude-$(id -u)/t.sql && head -3 /tmp/claude-$(id -u)/t.sql
# before: "-- Source: /home/..."; after: "-- Source: db_patches/tables.json"
composer phpunit:entrypoint -- tests/phpunit/maintenance/includes/SchemaGeneratorTest.php
composer phpunit:entrypoint -- --testsuite=structure   # core's AbstractSchemaTest, on core's paths
```

## 2. api-testing `ReparseDependentPages.js` fails with Parsoid read views

### What fails

`npm run api-testing` in core gives 18 failures. 17 are the known REST
`Content-Type` failures (`sbx/upstream/PHAB-TASK-1.md`). The 18th failed
in each of 3 runs:

```
  18) Reparse of dependent pages
       should create a page with missing template and link:
     AssertionError: expected '<div class="mw-content-ltr mw-parser-…' to match /title=Template(:|%3A)TemplateXSpwgOUwgj&amp;action=edit&amp;redlink=1/
      at Context.<anonymous> (tests/api-testing/action/ReparseDependentPages.js:20:10)
```

This is what the wiki renders for a red-linked template:

```
href="http://localhost:4000/index.php/Template:TemplateNoSuchXyz?action=edit&amp;redlink=1"
```

### History and cause

- `f1a7d0b5f6e` (2026-10-09, "Make tests agnostic to choice of parser
  (legacy or Parsoid)", T432762) changed the first assertion to
  `title=Template(:|%3A)${ template }&amp;action=edit&amp;redlink=1`.
  The new regex accepts the encoded colon, but it still expects a
  `?title=` URL.
- `87bc95497cb` (merged 2026-10-12, "Set default for wgUseParsoidParser
  to true", T432762, T440814) made Parsoid render read views by default.

The legacy parser writes a red link as
`$wgScript?title=Template:X&action=edit&redlink=1`. In this sandbox,
Parsoid writes it as `$wgArticlePath` plus a query:
`/index.php/Template:X?action=edit&redlink=1`. The test's regex accepts
only the first form. The second assertion (the plain link,
`title=${ link }&amp;action=edit&amp;redlink=1`) has the same problem.
It did not fail only because the test stopped at the first assertion.

### Find out first: why CI passes

`87bc95497cb` and the changes after it passed CI, so CI renders a form
that the regex accepts. There are two possible reasons:

- Quibble's settings template (`integration/quibble`,
  `quibble/mediawiki/local_settings.php.tpl`, line 50) says "Parsoid
  does not yet work in Quibble", and Quibble loads Parsoid only when
  `services/parsoid` is cloned. So the read views in core's CI jobs
  possibly still come from the legacy parser, and this test has not run
  against Parsoid read views in CI. This is the more likely reason.
- The article path. The sandbox does not set `$wgArticlePath`, and
  `composer serve` is PHP's built-in server, so the sandbox uses the
  path-info form `/index.php/$1`. CI may use a different form.

Find out which reason is correct before you write the fix, and say it in
the commit message. If CI does not run Parsoid read views, the failure
is latent, and CI will hit it when Quibble starts to use Parsoid. That
is a good reason to fix it now.

### Proposed fix

Make the two assertions accept both URL forms. This regex matches the
page part of the link:

```js
const redlink = ( page ) => new RegExp(
	`(title=${ page }&amp;|/${ page }\\?)action=edit&amp;redlink=1`
);
assert.match( html, redlink( `Template(:|%3A)${ template }` ) );
assert.match( html, redlink( link ) );
```

Another option tests the meaning, not the form. Parse the HTML, find the
`<a>` whose `title` attribute names the page, and check that it has the
`new` class and that its `href` has `action=edit` and `redlink=1`. Use
this if the reviewers prefer it.

### How to test

```bash
cd "$MW_INSTALL_PATH"
(composer serve >/tmp/claude-$(id -u)/serve.log 2>&1 &)   # if the wiki is not running
npx mocha --timeout 0 tests/api-testing/action/ReparseDependentPages.js
# before the fix: 1 failing; after: passing
npm run api-testing   # 17 failures remain (the REST Content-Type ones)
```

(`npm run api-testing` runs `mocha --timeout 0 --recursive --parallel
tests/api-testing`.) Also run the test once with
`$wgUseParsoidParser = false;` in `LocalSettings.php`, to show that the
legacy form still passes. Then remove the line.

## 3. `UndoIntegrationTest::testMcrUndoAction` has no title in its context

### What fails

`composer phpunit:entrypoint -- --testsuite=integration` gives 4 errors,
one for each data set of `UndoIntegrationTest::testMcrUndoAction`:

```
1) MediaWiki\Tests\Storage\UndoIntegrationTest::testMcrUndoAction with data set "undoing a single revision" (array('1', '2'), '1', 0, 1, true, 1, 1, 0)
Error: Call to a member function inNamespace() on null
/home/cananian/Projects/Wikimedia/EventLogging/includes/JsonSchemaHooks.php:82
/home/cananian/Projects/Wikimedia/core/includes/HookContainer/HookContainer.php:127
/home/cananian/Projects/Wikimedia/core/includes/HookContainer/HookRunner.php:1646
/home/cananian/Projects/Wikimedia/core/includes/Actions/McrUndoAction.php:416
```

This is not a new regression. Neither side has changed in a way that
causes it: `JsonSchemaHooks.php` last changed in April 2026, and
`McrUndoAction.php` in July 2026. The error occurs when EventLogging is
loaded.

### Cause

In `tests/phpunit/integration/includes/Storage/UndoIntegrationTest.php`,
`testMcrUndoAction()` makes
`$context = new DerivativeContext( RequestContext::getMain() )`, sets
the user, and gives it to `Article::newFromTitle()` and
`makeNewMcrUndoAction()`. It does not call `$context->setTitle()`. The
other test in the same file, `testMcrUndoActionWithTempUser()`, does
call `$context->setTitle( $article->getTitle() )`.

`McrUndoAction::onSubmit()` (around line 416) runs the
`EditFilterMergedContent` hook with `$this->getContext()`, which has no
title. EventLogging's handler (`JsonSchemaHooks::onEditFilterMergedContent`)
calls `$context->getTitle()->inNamespace( NS_SCHEMA )` on that context.
It reaches this line on every wiki except the one named by
`$wgEventLoggingDBname` (default `metawiki`). In a real request, the
context always has a title, so only the test is wrong.

### Proposed fix

In `testMcrUndoAction()`, after the `Article::newFromTitle()` line, add
`$context->setTitle( $article->getTitle() );`, as
`testMcrUndoActionWithTempUser()` does. Then the hook gets the context
that a real request gives it.

Optional and separate: EventLogging's handler could also check for a
null title. That change goes in mediawiki/extensions/EventLogging, on
its own branch, and it is not needed for this fix.

### How to test

The failure needs EventLogging to be loaded, which is so in this
sandbox:

```bash
cd "$MW_INSTALL_PATH"
composer phpunit:entrypoint -- tests/phpunit/integration/includes/Storage/UndoIntegrationTest.php
# before the fix: 4 errors; after: OK
```

## 4. `WikiBirthdayTest` does not clear the `GetHumanTimestamp` hook

### What fails

`composer phpunit:entrypoint -- --testsuite=maintenance_suite` gives 2
failures:

```
1) MediaWiki\Tests\Maintenance\WikiBirthdayTest::testExecuteForOneRevision
Failed asserting that 'Wiki was created on: 1 year ago <age: 1 yr(s), 0 month(s), 0 day(s) old>.\n
' matches PCRE pattern "/Wiki was created on: 5 April 2023.*age: 1 yr.*0 month.*0 day.*old/".
2) MediaWiki\Tests\Maintenance\WikiBirthdayTest::testExecuteForDeletedRevision
Failed asserting that 'Wiki was created on: 2 months ago <age: 0 yr(s), 2 month(s), 3 day(s) old>.\n
' matches PCRE pattern "/Wiki was created on: 5 May.*age: 0 yr.*2 month.*3 day.*old/".
```

This is not a new regression. The test (`0532313deb`, August 2024)
fails when the cldr extension is loaded.

### Cause

`maintenance/wikiBirthday.php` formats the date with
`Language::getHumanTimestamp()`. That function runs the
`GetHumanTimestamp` hook first, and it uses core's own format
(`getHumanTimestampInternal()`: "5 April 2023") only when no handler
returns false. cldr (`includes/Hooks.php`,
`onGetHumanTimestamp`) handles this hook, and it always gives a relative
time ("1 year ago") when it has translations for the language. The
test expects core's format, and it does not remove other handlers of
the hook.

### Proposed fix

In `tests/phpunit/maintenance/WikiBirthdayTest.php`, add a `setUp()`
that calls `$this->clearHook( 'GetHumanTimestamp' );`
(`MediaWikiIntegrationTestCase::clearHook`). Then the test checks
core's format no matter which extensions are loaded.

The maintenance script itself is not wrong. A relative date is a valid
output on a wiki with cldr. If reviewers want the script's output to
stay the same on every wiki, that is a different change, and it gets its
own task.

### How to test

The failure needs cldr to be loaded, which is so in this sandbox:

```bash
cd "$MW_INSTALL_PATH"
composer phpunit:entrypoint -- tests/phpunit/maintenance/WikiBirthdayTest.php
# before the fix: 2 failures; after: OK
```
